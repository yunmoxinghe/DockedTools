# 一次开发，多浏览器兼容：最佳实践 + 本项目差距

调研时间 2026-10-01。结论均标注来源，版本相关的以官方原文为准。

> **2026-10-01 晚：本文第二节的 P0 与 P1 项已落地**，改动见本文末尾《落地记录》。
> 第三节 Safari 与配对令牌仍未做，理由写在《为什么配对令牌暂不实现》。

## 一、行业共识的最佳实践

### 1. 一套源码 + 构建期生成各平台 manifest

**不要**手维护多个目录（会快速分叉），也**不要**在一个 manifest 里塞满条件判断。

共享的部分：功能逻辑、数据模型、存储模块、校验、popup/设置 UI、多语言、单测。
分开的部分：manifest 变体、扩展 ID、最低版本、后台声明、部分权限、图标与商店素材、打包签名发布脚本。

> 来源：polprog《Chrome vs Firefox vs Edge vs Safari: what we learned from shipping 9 browser extensions》
> 「A shared manifest would therefore be artificial savings. It is easier to maintain a few small, explicit differences than one file full of exceptions and conditions.」

### 2. 命名空间：现在不乱用就行，不必强上 polyfill

- Chrome / Edge：`chrome.*`，MV3 下异步 API 已返回 Promise（Chrome 121 起，devtools_page 例外到 152）
- **Chrome 148（2026 年中）起原生支持 `browser.*` 命名空间**；带 devtools_page 的扩展要到 Chrome 152
- Firefox：`browser.*` 原生带 Promise，`chrome.*` 是**不带 Promise** 的别名
- Safari：两者都支持，但只有 `browser.*` 给 Promise
- **Chrome 152+ 时 webextension-polyfill 变成 no-op**

> 来源：MDN《Build a cross-browser extension》、Firefox Extension Workshop《Browser compatibility》

**对本项目的判断**：现有代码用 `chrome.*` + 回调风格，在三家都能跑（Firefox 的 chrome.* 别名支持回调）。
**不需要**为了兼容性引入 polyfill。要引入的唯一理由是想要 Promise 化，那是代码风格问题不是兼容问题。

### 3. 后台模型：Chrome/Safari 是 service worker，Firefox 是 event page

| | Chrome 120+ | Firefox 121+ | Safari 17+ |
|---|---|---|---|
| 上下文 | Service worker | **Event page 或 worker** | Service worker |
| 空闲回收 | ~30s | 不确定 | ~30s |
| 有 DOM | 否 | **event page 有** | 否 |
| 全局变量存活 | 否 | **常见情况存活** | 否 |

关键不对称：**为 Chrome 写的代码能在 Firefox 跑，反过来不行**。因为 Firefox 的 event page 保留了 Chrome
service worker 没有的 `window` / `document` / `DOMParser` / `localStorage`，在 Firefox 上"能用"的写法
到 Chrome 直接抛。

安全的写法只碰这两层：**`fetch` / `crypto` / `TextDecoder` / `URL`** 和 **`chrome.*` 扩展 API**。

> 来源：moderok《Firefox Manifest V3 Uses an Event Page, Not a Service Worker》、
> mv3-extension.com《Background Script Support Across Browsers》

**两条三家通吃的铁律**：
1. **监听器必须在顶层同步注册**。放在 `await` 之后的监听器等背景被唤醒时还不存在，事件直接丢失。
2. **定时器不跨休眠**。要延时用 `chrome.alarms`，不要用 `setTimeout`。

### 4. 能力检测，不要浏览器嗅探

`storage.sync` 在 Safari 上受限（iCloud 支撑、节流更严），`storage.local` 上限 Safari 只有 5 MB
（Chrome/Firefox 是 10 MB）。检测 API 是否存在再降级，别去判断 UA。

### 5. 权限最小化 + 可选权限

Chrome Web Store 要求每个权限都有正当理由，权限过宽会被拒。能用 `activeTab` 就别申请全站，
非核心功能用 `optional_permissions` 运行时再要。

### 6. Chrome 绿 ≠ 兼容

只在 Chrome 测过，只证明了和 Chromium 兼容。没证明：Gecko 行为、WebKit 行为、不同的 popup 生命周期、
不同的权限模型、图标缩放、API 语义一致。

> 来源：polprog 同文：「Chrome is a good starting point, but a poor only testing environment」

## 二、本项目当前差距（按严重度排序）

### 🔴 P0-1：缺 `content_security_policy` → Firefox 上 `ws://` 会被静默升级成 `wss://`

**这是会让 Firefox 直接连不上桥接的问题，而且不报有意义的错。**

MV3 的默认 CSP 里包含 `upgrade-insecure-requests`，会自动把 `http:` → `https:`、`ws:` → `wss:`。
Chrome 的默认 CSP **不含**这一项，Firefox **含**。本项目的 `manifest.json` 没有声明
`content_security_policy`，所以走默认：Chrome 正常，Firefox 上 `ws://127.0.0.1:17829/bridge`
被升成 `wss://`，而服务端是裸 WebSocket → 握手失败。

表现会很迷惑：**端口扫描能扫通（那是 TCP），握手失败**，而且错误信息不会指向 CSP。

修法 —— 覆盖默认 CSP，去掉该指令：

```json
"content_security_policy": {
  "extension_pages": "script-src 'self'; object-src 'self';"
}
```

两个都写的原因：Chromium 强制要求 `object-src` 必须显式声明且只允许安全资源，缺了会报
「CSP directive 'object-src' must be specified」；Firefox 需要 `script-src 'self'`。

> 来源：MDN《Content Security Policy》「Manifest V3 Extensions that need to make http: or ws: requests
> can opt out of this behavior by overriding the default CSP ... excluding the upgrade-insecure-requests directive」；
> 真实案例 MALSync issue #2486：「the default CSP in MV3 in Firefox is "script-src 'self';
> upgrade-insecure-requests;". This is different than on Chrome.」
> ⚠️ 另注：Firefox 的 **HTTPS-Only 模式**也会强制升级，但默认豁免回环地址，通常不影响本场景。

### 🔴 P0-2：`StrictWhitelist` 严格模式在 Firefox 上**根本无法实现**

Firefox 扩展的 Origin 是 `moz-extension://<UUID>`，这个 UUID 是**每台机器随机生成**的
（Mozilla 明确说是出于隐私考虑），**与 `browser_specific_settings.gecko.id` 无关**，服务端无法预知也无法枚举。

也就是说 `BridgeConfig.StrictWhitelist` 里无论填什么，Firefox 上都匹配不上 → 严格模式一开，
Firefox **100% 连不上**。

> 来源：Mozilla 官方支持论坛（cor-el  moderator）：「You can't identify an extension because the UUID
> is random and unique in each case」；MDN《permissions》：
> 「url moz-extension://60a20a9b-.../ 其中 ... 是扩展的**内部 ID**」。

**这意味着 `RequiresPairing` 不只是"第三关还没启用"，它是跨浏览器唯一能精确识别客户端的手段。**
真实项目（Hister）的做法正是：Chrome 上精确匹配静态 ID，Firefox 上只能退化为前缀匹配
`moz-extension://`（代价是无法区分"你的扩展"和"任意其他 Firefox 扩展"），
要精确校验就只能引入**用户手工配置的共享密钥**。

建议的认证分层：

| 层 | 挡什么 | Chrome | Firefox |
|---|---|---|---|
| Origin 前缀校验 | 冒充的网页（页面 JS 伪造不了 Origin） | ✅ | ✅ |
| 精确 ID 白名单 | 其他扩展 | ✅ | ❌ 做不到 |
| 配对 token | 本机其他进程（能伪造任意 Origin 头） | ✅ | ✅ 唯一出路 |

### 🟠 P1-1：缺 `data_collection_permissions` → AMO 提交会失败

**2025-11-03 起，提交到 AMO 的新扩展必须声明**。当前 manifest 没有这一项。
MDN 原文：*Must be provided with `data_collection_permissions` for new extension submitted to
addons.mozilla.org from November 3, 2025.*

```json
"browser_specific_settings": {
  "gecko": {
    "id": "dockedtools-bridge@example.invalid",
    "strict_min_version": "142.0",
    "data_collection_permissions": { "required": ["none"] }
  }
}
```

⚠️ 连带坑：这个键只在 **Firefox 桌面 140 / Android 142** 起支持，`strict_min_version` 低于 142
会触发 `KEY_FIREFOX_UNSUPPORTED_BY_MIN_VERSION`（先报桌面再报 Android）。当前写的 `121.0` 必定 lint 失败。

### 🟠 P1-2：`strict_min_version: "121.0"` 太低

MDN 备注：**能接收更新的最低版本是 115.0 (ESR)，或不含 ESR 时 128.0** —— 因为 2025 年 3 月根证书过期，
更老的 Firefox 认不出扩展签名。配合上面 P1-1，`142.0` 才是能同时满足的地板。

### 🔴 P2-1 已升级为 P0：Firefox **必须**用 event page（不是"建议"）

> **2026-10-01 更新**：这条原本标 🟡「建议」，真机 `web-ext lint` 之后升级为 🔴。
> Firefox **不支持** `background.service_worker`（bug 1573659 未实现），
> 只写它的后果是后台脚本一次都不执行。详见「六、落地记录」第 4 条和「七、真机验证」。

```json
"background": {
  "service_worker": "background.js",
  "scripts": ["background.js"],
  "type": "module"
}
```

⚠️ **连锁依赖**：Chrome **121 之前会拒绝加载**含 `background.scripts` 的 MV3 扩展。
当前 manifest 写着 `"minimum_chrome_version": "116"` —— 一旦双写，`minimum_chrome_version`
必须提到 **121**，否则 Chrome 116~120 直接装不上。

> 注：也有资料建议不要双写（验证引擎可能告警）。主流做法（MDN / moderok / mv3-extension.com）
> 是双写 + 卡版本下限。若要绝对稳妥，就走构建期按 target 生成 manifest（见最佳实践第 1 条）。

### 🟡 P2-2：gecko id 建议换成自有域名

当前 `dockedtools-bridge@example.invalid`。`.invalid` 是 RFC 2606 保留 TLD，格式上符合
MDN 的正则 `^[a-zA-Z0-9-._]*@[a-zA-Z0-9-._]+$`，AMO 也能过。但 MDN 示例用 `extensionname@example.org`，
且 AMO 首次签名会**检查 ID 唯一性**。建议换成自己控制的域名，避免撞车。

## 三、Safari 的现实成本

Safari 不是"改改 manifest 就能上"：**需要 Xcode 工程和一个宿主 App**，Apple 提供 `safari-web-extension-converter`
但产物仍要当原生工程做签名和 App Store 分发。且 `safari-web-extension://` 前缀的 Origin
同样是**每机随机**，跟 Firefox 一个处境。

**建议**：先把 Chrome/Edge + Firefox 跑通，Safari 单独立项评估。

---

## 四、落地顺序建议

1. 加 `content_security_policy`（一行，决定 Firefox 能不能连）—— 但本机没有 Firefox，**无法实测**，
   只能靠 MDN 与真实案例推断，装 Firefox 后必须真机验一次。
2. 加 `data_collection_permissions` + 把 `strict_min_version` 提到 `142.0`。
3. 上配对 token（这是唯一跨浏览器可用的身份校验，顺带补上 `RequiresPairing = false` 的缺口）。
4. 引入构建期 manifest 生成（`build.mjs` 里加 target 参数），替代手改。
5. Safari 单独立项。

---

## 五、结论一句话

**Chrome 绿不等于兼容。** 本项目最大的两个坑都不是"代码写法"问题：
一个是**默认 CSP 差异**（Firefox 上 ws 被静默升级，现象极具迷惑性），
一个是**Firefox 的 Origin 天生不可白名单**（白名单这条路在 Gecko/WebKit 上根本走不通）。

## 六、落地记录（2026-10-01 晚）

### 已改

**1. `content_security_policy`（P0-1，已修）**

`src/manifest.json` 加了：

```json
"content_security_policy": { "extension_pages": "script-src 'self'; object-src 'self';" }
```

`object-src` 是 Chromium 强制的（缺了报 "must be specified"），`script-src` 是 Firefox 要的。
已加**回归断言**：`e2e.mjs` 会检查两个 target 的 CSP 里**都不含 `upgrade-insecure-requests`**，
以后谁手滑加回去会立刻红。

**2. 构建改成按目标生成（P1 的前置，也是最佳实践第 1 条）**

- `tsconfig.json` 的 `outDir` 从 `dist` 改成 `dist/_build`（中间产物）
- `build.mjs` 重写：从 `dist/_build` + `src` 组装出 `dist/chrome` 与 `dist/firefox`，各写各的 manifest
- `src/manifest.json` 只剩**共享部分**（不再塞 `browser_specific_settings`）
- Firefox target 自动注入 gecko id / `data_collection_permissions` / `strict_min_version: 142.0`，
  并**剥掉** `minimum_chrome_version`

这样 `minimum_chrome_version` 可以**继续留在 116**：chrome target 里没有 `background.scripts`，
不会触发"Chrome 121 之前拒绝加载"那条限制。这是分 target 带来的实际收益，
不是靠在一个文件里妥协换来的。

**3. 严格模式重写成按 scheme 分级（P0-2，已修）**

新增 `OriginVerdict` / `ExtensionOriginKind` 两个枚举和 `BridgeConfig.CheckOrigin`：

| Origin | 判定 |
|---|---|
| `chrome-extension://` 命中白名单 | `Allowed` |
| `chrome-extension://` 不在白名单 | `Rejected` |
| `moz-extension://` / `safari-web-extension://` | **`AllowedUnverifiable`**（放行 + 打告警日志） |
| 网页 / 无 Origin | `Rejected`（严格模式下） |

`IsAllowedOrigin` 保留为兼容包装（`!= Rejected`），现有调用方不用动。

**关键收益**：`StrictOriginWhitelist` 从"一开就全死"变成了**真的可以打开**。
之前它对 Firefox 是 100% 拒绝，没人敢开，安全能力等于零；
现在 Firefox 降级放行并留痕，Chrome 照旧精确匹配。

`RequiresPairing` 的注释也重写了，把它从"第三关还没做"改成
"唯一能跨浏览器精确识别客户端的手段"，并写明启用它两端都要做什么。

**4. Firefox 必须有 `background.scripts`（本轮真机验收翻出来的新 P0，已修）**

这一条**推翻了上一版文档里"Firefox 也用 service_worker"的判断**，而且是关键性的：

```
web-ext lint dist/firefox
ERRORS: BACKGROUND_SERVICE_WORKER_NOFALLBACK
"/background/service_worker" 必须与 "/background/scripts" 配对才能兼容 Firefox。
```

MDN `manifest.json/background` 原文：**Firefox 不支持 `background.service_worker`**
（bug 1573659 仍未实现）。只声明 `service_worker` 的后果**不是降级，而是后台脚本一次都不会被执行** ——
扩展在 Firefox 上全废，而且没有任何报错。上一版那句"后台不碰 DOM，所以符合最低公共分母"
是站不住的：问题不在代码能不能跑，在于**压根不会被加载**。

正确写法是两者并列：

```json
"background": {
  "service_worker": "background.js",
  "scripts": ["lib/bridge.js", "background.js"]
}
```

按浏览器分：Chrome 用 `service_worker`，Firefox 忽略前者走 `scripts`（event page），
Safari 两者都有时默认用 `scripts`。

**但 Chrome 那侧绝不能带 `scripts`**：Chrome 121 起忽略 MV3 里的 `background.scripts`，
121 之前是**拒绝加载整个扩展**。我们声明 `minimum_chrome_version: 116`，
带上就是把 116~120 的用户直接挡在门外。所以：**Firefox 两份都写，Chrome 只写 service_worker** ——
这条只能靠分 target 实现，一个文件凑不出来。

**5. `background.ts` 的 bridge 加载改成兼容两种环境（已修）**

Firefox 走 event page 时，`lib/bridge.js` 是由 manifest 的 `scripts` 数组**先**加载的，
轮到 `background.js` 时 `DockedBridge` 全局已经挂好了。所以 `loadBridge` 的顺序必须是：

1. 先查 `globalThis.DockedBridge` 在不在，在就直接用（event page 路径）
2. 不在才尝试 `importScripts`（service worker 路径）
3. 两条路都走不通就抛带诊断的错，绝不静默

**真机实测：Firefox event page 里 `typeof importScripts === false`**。
所以"无条件 `importScripts`"的写法在 Firefox 上必然炸 —— 而且炸法很难查：
后台起不来、popup 永远显示"未连接"，真错误被吞掉。

### 为什么配对令牌暂不实现

做了威胁建模之后判断**收益被高估、代价被低估**，所以没动：

- **主威胁是恶意网页**。这一条已经被 Origin 前缀校验挡死了 ——
  Origin 头由浏览器强制附加，页面 JS 伪造不出 `moz-extension://` 前缀。**已经解决**。
- **残余威胁是本机其他进程**。但本机进程能伪造任意 Origin 头，
  而且它们有更省事的路：直接改写 `%LOCALAPPDATA%` 里的 `web-shortcuts.json`。
  也就是说精确白名单/配对**挡不住真正想搞事的本机进程**。
- 配对要两端同时实现才有意义，只开服务端会把扩展直接锁在外面；
  而且要真正做到"首次配对可信"，需要用户在 popup 里确认（否则就是 TOFU，
  恶意客户端抢先连上就成了"第一个"）。这要动协议 + UI，属于架构级改动，不该擅自动。

**什么时候该做**：当桥接开始承载比"增删快捷方式"更敏感的操作，
或者要防的不是网页而是同机其他软件时。

## 七、真机验证（2026-10-01 夜，Firefox 157.0 release）

上一版文档结尾写着"本机没有 Firefox，CSP 那条只能靠推断"。现在装了，**全部实测了**。
工具链：Mozilla 官方 `web-ext` 10.7（release 通道的 Firefox 只能靠 DevTools 临时加载，
未签名 XPI 装不进去，这正好是 web-ext 干的事）。

### CSP × 主机权限矩阵（`node 测试/火狐真机探针/run.mjs`）

服务端用**裸 TCP** 而非 WebSocket 库，因为它要分辨浏览器到底发了什么：
TLS ClientHello（`0x16 0x03…`）= 被 CSP 升成 wss；HTTP + `Upgrade: websocket` = 正常握手。

| | 无 `host_permissions` | 有 `ws://127.0.0.1:*/*` |
|---|---|---|
| **默认 CSP** | ❌ 被升成 wss | ❌ 被升成 wss |
| **覆盖 CSP**（我们的写法） | ✅ ws 连上 | ✅ ws 连上 |

1. **P0-1 坐实**：默认 CSP 真的会把 `ws://` 静默升成 `wss://`，CSP 覆盖是必需项。
2. **不需要 `host_permissions`**：无权限照样连上，manifest 不用补，少一项权限少一份风险。
3. **Origin 确为 `moz-extension://<每机随机 UUID>`**：四次运行四个不同 UUID
   （`872796d8…` / `2ce70613…` / `c61951b6…` / `6ef9db3b…`），与 `gecko.id` 无关
   ⇒ 技术上不可能进白名单，**P0-2 的降级放行设计是对的**。

### 真实产物端到端（`node 测试/火狐真机探针/real-e2e.mjs`）

`dist/firefox` 原封不动装进真 Firefox（只追加探针脚本），连真的 C# 桥接服务端跑完整协议：
`hello` 握手带回服务端信息、中文 ping 往返一致、`webapp.list` 返回数组 —— **6 / 0 通过**。

顺带验了最难的一条：`background.ts` 里那段 `loadBridge` 的分支，

### 这一节里最贵的一条教训

真机跑之前，我在这份文档里写过一句**后来被证明是错的**结论：
"Firefox 也用 service_worker，后台代码不碰 DOM，符合最低公共分母，代码里一个分支都不用加。"
它看起来很合理，但它把"**符合**最低公共分母"当成了"**会是**那个分母" ——
Firefox 压根不会去加载 `service_worker`，代码写得再兼容也轮不到它跑。

**推断出来的结论和实测出来的结论之间，差一个 4 分钟的 `web-ext lint`。**
凡是能用工具判定的，别用人脑判。
