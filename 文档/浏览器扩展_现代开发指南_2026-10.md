# 浏览器扩展现代开发指南（2026-10 联网核实版）

调研时间 2026-10-02。所有版本相关结论都以官方原文为准并标注来源。
本文是 `浏览器扩展_多浏览器兼容最佳实践.md` 的**增量**，不推翻它——它里面 CSP / Firefox event page /
Origin 白名单那几条已经真机验过了。本文补的是它**没覆盖或已过时**的部分。

## 1. Chrome 的新基线：148

Chrome 148（2026 年中）是这轮最大的一次平台变化，一次给了三样东西。

### 1.1 browser 命名空间 —— 新扩展的官方推荐默认

> 「If you're building a new extension, set `minimum_chrome_version` to `"148"` and use `browser`
> unconditionally; you can stop reading here.」
> —— developer.chrome.com《Transition to browser namespace》

- `browser.tabs === chrome.tabs`，同一批 API 对象，两个命名空间长期共存
- 源自 W3C 社区组 **WECG**（WebExtensions Community Group），是浏览器厂商协作的共享标准
- Chrome 152 起带 `devtools_page` 的扩展也能用（148~151 是全局关闭的）
- **webextension-polyfill 在 148+ 变成 no-op**。Chrome 136 那次回滚就是因为 polyfill 见到 `browser`
  就停止包装、而当时 Chrome 的 `onMessage` 还给不出 Promise；148 把两者一起发了，gap 已补上

**这意味着"为了兼容要引入 polyfill"这个老结论过期了**：现在只需把 `minimum_chrome_version`
抬到 148，直接写 `browser.*`，Chrome / Firefox / Safari 三家**同一套代码、都是 Promise**，不用 polyfill。

### 1.2 onMessage 可以直接返回 Promise

```js
// 旧：return true + 稍后 sendResponse
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  doAsync().then(sendResponse);
  return true;
});

// 新（Chrome 148+）：直接 async
browser.runtime.onMessage.addListener(async (msg) => {
  return await doAsync();
});
```

`return true` 模式继续有效，但新代码没必要再写。`chrome.*` 调用同样生效。

### 1.3 消息序列化可选 structured_clone

```json
{ "message_serialization": "structured_clone" }
```

Chrome 148+ opt-in。JSON 序列化下会丢的 `Map` / `Set` / `Date` / `BigInt` / `Error` / `Blob`
现在能原样过。坑：结构化克隆**忽略 `toJSON()`**（靠 `toJSON` 脱敏的对象会把敏感字段一起带过去）；
`SharedArrayBuffer` 不支持；扩展间通信两侧格式必须一致，不一致直接断端口；
**原生消息通道强制 JSON**。
> 来源：developer.chrome.com blog《Unlock Structured Clone for Chrome Extension Messaging》

### 1.4 其他近期变化（来自官方 whatsnew）

- Chrome 150：`chrome.contextMenus` 支持 `"tab"` context（标签栏右键）
- Chrome 150：`chrome.alarms.create()` 对 alarm 名加 1024 字节上限，超了抛 TypeError
- Chrome 153：新增 `browser.publicSuffix`；**实验性**默认把扩展图标 pin 到工具栏

## 2. 后台模型：三引擎的老差异没变，但可以简化了

| | Chrome 120+ | Firefox 121+ | Safari 17+ |
|---|---|---|---|
| 上下文 | Service worker | **Event page**（`background.service_worker` 不被加载） | Service worker |
| 空闲回收 | ~30s | 不确定 | ~30s |
| 有 DOM | 否 | event page 有 | 否 |

关键不对称仍然是：**为 Chrome 写的代码能在 Firefox 跑，反过来不行**。
只碰 `fetch` / `crypto` / `TextDecoder` / `URL` + 扩展 API，就三家通吃。
> 来源：MDN `manifest.json/background`（bug 1573659 仍未实现）；mv3-extension.com 对照表

### 2.1 `type: "module"` 三家都支持了

- Chrome：MV3 起就支持（module worker 里 `importScripts` 会抛，用 `import`）
- Firefox：`background.scripts` + `type: "module"` 自 **121** 起支持
- Safari：自 **16.4** 起支持

**这条能砍掉一大堆历史包袱**。开了 ESM 就不需要 `importScripts` 加载桥接库、不需要
`namespace` + IIFE 挂全局、不需要"这个文件不能出现 import/export"的约束。
> 来源：mv3-extension.com《Using ES Modules in an MV3 Service Worker》

### 2.2 双写 background 的前提变了

```json
"background": { "service_worker": "background.js", "scripts": ["background.js"] }
```
Chrome 121 起**忽略** MV3 里的 `scripts`，121 之前是**拒绝加载整个扩展**。
所以只要 `minimum_chrome_version >= 121`，就能**一份 manifest 双写通吃**，
不再需要"Chrome target 只写 service_worker、Firefox target 两份都写"的构建期分叉。
（分 target 仍是最稳妥的做法，但不再是唯一的做法。）

## 3. ⚠️ 纠偏：Local Network Access 不适用于扩展

这是本次调研里**和现有代码假设冲突最严重**的一条。

Google 官方《LNA Adoption Guide》原文：

> 「We do not currently have plans to apply LNA restrictions to extensions.
> Currently, extensions that have the necessary host permissions are allowed to make
> local network requests.」

补充事实：
- LNA 自 **Chrome 142** 起对网页默认生效（subresource / fetch / 子框架导航）
- **Chrome 147 起才把 WebSockets、WebTransport 纳入**（这就是之前"142 覆盖 fetch、147 才覆盖
  WebSocket"那个分阶段说法的来源）
- 权限名在 Chrome 145 拆成 `local-network` 和 `loopback-network`（145 前是单个
  `local-network-access`）
- **扩展在豁免名单里**

本分支 `popup.ts` / `bridge.ts` / `background.ts` 顶部那一大段关于
"chrome-extension:// 是 public origin → 连 127.0.0.1 要过 LNA → SW 触发不了首次弹窗 →
必须由 popup 在用户手势下触发"的设计，**建立在一个对扩展不适用的前提上**。
好消息是代码里 2026-10-01 的实测结论已经写明了："当前版本回环 WebSocket 处于'可查权限但
实际放行'状态" —— 实测是对的，只是官方口径比这更强：**压根没计划管扩展**。

那套"申请本机访问权限"按钮 + `triggerPermissionPrompt()`（故意发一次必失败的 fetch 去骗弹窗）
属于为不存在的约束做的过度设计，建议删。

## 4. 工具链：2026 年的默认答案

| 工具 | 定位 | 2026 现状 |
|---|---|---|
| **WXT** | 完整框架，Vite 底座 | **推荐默认**。0.21.4（2026-08-11），Node 要求 ≥ 22。自动 manifest、多浏览器 target、HMR、`wxt zip` 直接出商店包 |
| CRXJS | Vite 插件，只解决打包 | 2.7.0（2026-06-19）已 stable，Vite 团队首选 |
| Plasmo | React 优先 | 自 2025-05-17 起无提交，v0.90.5 后无发版，**维护模式**。新项目别选 |
| Extension.js | 零配置 CLI | 还不够成熟 |

WXT 注意点：它**不自带 messaging 封装**（要用 `@webext-core/messaging`），
`wxt/browser` 只是 `globalThis.browser ?? globalThis.chrome` 的别名不是真 polyfill，
所以还是要能力检测而不是信类型。
> 来源：merginit.com《Plasmo vs WXT vs CRXJS vs Extension.js》(2026-08-23)；hivebook WXT 词条

## 5. UI 形态：popup 关掉就没了

| 形态 | 生命周期 | 适用场景 |
|---|---|---|
| **popup** | 点开即建、失焦即毁 | 一次性操作 |
| **side panel** | 常驻，跨标签保持 | 需要持续展示/持续连接 |
| offscreen document | 短命，只跑 Web API | DOM / 音频等 SW 干不了的活 |

`chrome.sidePanel` 是 Chrome 官方给"持久界面"的答案。声明 `side_panel.default_path` **不会**
让它可打开——必须配一个触发器（`action.onClicked` 里 `chrome.sidePanel.open()`，或
`setPanelBehavior({ openPanelOnActionClick: true })`；注意是 `openPanelOnActionClick`，
写成 `...IconClick` 会同步抛 TypeError 悄悄干掉 SW）。

对"保持与本机 app 的长连接"这种需求，popup 是错的选择：它一关，UI 状态全丢，
SW 还要在 30s 后被回收。

## 6. 商店上架硬要求

- **icons 必须 16 / 32 / 48 / 128 四个尺寸的**真实 PNG**。缺了 Chrome 用默认灰方块，商店直接拒。
- 至少 1 张 1280×800 或 640×400 截图
- 隐私政策 URL 必须可访问且与数据使用披露一致
- 每个 permission / host_permission 都要一句人话理由（"needed to work" 会被拒）
- 打包 zip 排除 `.git/` / `node_modules/` / `.env`
- AMO 侧：2025-11-03 起新提交强制 `data_collection_permissions`，
  连带把 `strict_min_version` 顶到 **142.0**
> 来源：chrome-extensions skill 的 pre-publish checklist；dev.to 三商店同源发布实践

## 7. 本分支差距清单（按严重度）

### 🔴 P0-1：完全缺 icons

`src/manifest.json` 里没有 `icons`，`action` 里也没有 `default_icon`。
工具栏上是灰方块，商店提交过不了。这是最直观的"不行"。

### 🔴 P0-2：SW 里用模块级变量存状态，且存在竞态

`background.ts`：
```js
let cachedPort = 0;
chrome.storage.local.get(['bridgePort'], (r) => { cachedPort = Number(r.bridgePort) || 0; });
```
SW 冷启动后 `onMessage` 已注册、而 storage 回调可能还没回来 → `cachedPort` 还是 0 →
每次冷启动全量扫 11 个端口。官方铁律是 **SW 里不存状态，每个事件里现读 storage**。
改成：`browser.runtime.onMessage.addListener(async (msg) => { const { bridgePort } = await browser.storage.local.get('bridgePort'); ... })`

顺带：Chrome 122 起异步 API 已全部 Promise 化（官方 whatsnew 已确认），
`popup.ts` 里那个手写 `new Promise(resolve => chrome.runtime.sendMessage(msg, resolve))` 是多余的。

### 🟠 P1-1：为不存在的 LNA 约束写了 ~80 行

见第 3 节。`detectLoopbackPermission` / `triggerPermissionPrompt` / "申请本机访问权限"按钮 /
guide 提示块，都可以删。保留一个"连接失败"的普通错误提示就够。

### 🟠 P1-2：`minimum_chrome_version: "116"` 停在旧世界

116 的唯一理由是"Chrome 121 前会拒绝带 `background.scripts` 的 MV3"。
抬到 **148** 之后可以一次性拿到：browser 命名空间、onMessage 直接返回 Promise、
structured_clone、双写 background 也不再有版本顾虑。代价是 148 以下的用户收不到更新——
官方明确要求把这个当成**有意决策**并用分阶段发布，不是随手填的兼容值。

### 🟠 P1-3：没开 ESM，`loadBridge()` 那 30 行双环境 hack 是为 IIFE 打工的

`bridge.ts` 顶部写着"这个文件不能出现 import/export，所以用 namespace 编译成挂全局的 IIFE"，
`background.ts` 为了兼容"event page 已预加载 / SW 要 importScripts"两种路径写了分支。
开 `"type": "module"`（Chrome / Firefox 121+ / Safari 16.4+ 都支持）后直接 `import`，
两边都能删。

### 🟡 P2-1：UI 形态选了 popup，与"保持连接"的需求不匹配

见第 5 节。这是架构级选项，改不改要看产品意图——但如果"边栏助手配套扩展"是要常驻的，
side panel 才是对应形态。

### 🟡 P2-2：工具链是手写 tsc + 182 行 build.mjs

没有 HMR、没有 dev server、没有自动 zip。WXT 能一次性解决，且它本来就会按 target
生成 manifest，`build.mjs` 里那一整套 `MANIFEST_VARIANTS` 逻辑可以直接退休。
代价是引入框架依赖 + Node ≥ 22。

### 🟡 P2-3：Chrome 侧未验证的能力

- `chrome.alarms` 完全没用：注释里说"M0 先按需连，后续用 alarms 周期性唤醒"——
  注意 SW 休眠后 WebSocket 也保不住，alarms 只能做到**周期性重连**，做不到"app 主动推"
- Chrome 116+ 有"WebSocket 活跃时延长 SW 生命周期"的 keepalive（官方 known-issues 页），
  本项目没有显式依赖也没有压测过它的边界

## 8. 一句话结论

**2026 年的"现代"标准里，本分支落后的是基线版本（116 vs 148）和 UI/资源完整性（无 icons、
popup 形态），而不是 Firefox 兼容那套——那套它做得比大多数项目扎实。**
真正该动的第一刀：补 icons、把 SW 状态改成现读 storage、抬 `minimum_chrome_version` 到 148
并整体迁移到 `browser.*` + async onMessage（顺带删掉 `sendResponse` 样板和手写 Promise 包装），
再拆掉 LNA 那套过度设计。

## 9. WebExtensions 标准能覆盖掉这些差异吗？——不能，而且本项目踩的坑全在空白区

### 9.1 组织层面：2026 年确实升格了

**W3C 于 2026-05-12 正式成立 WebExtensions Working Group**（不再只是社区组 CG）。
Charter 期 2026-05-12 → **2028-05-12**，主席 Timothy Hatcher（Apple）+ Simeon Vincent，
每两周一次电话会。使命原文：*"specify the common core of cross-browser extension APIs"*。

但有三条硬限制写在 charter 里：

1. **只做 common core**。原文：*"We fully anticipate that browsers will offer APIs and
   capabilities beyond our common specifications."* —— 厂商超纲 API 是**被设计进去的**，
   不是待消除的缺陷。
2. **交付物是 Candidate Recommendation Snapshots，明确不进 Recommendation**：
   *"does not intend to advance their documents to Recommendation"*。
   也就是即便写完，也没有"W3C 推荐标准"地位，是活快照。
3. **明确 out of scope**：打包格式、签名方式、**扩展商店**、UI 具体形态。
   也就是说上架要求（icons 尺寸、截图、隐私政策、权限理由）永远不在标准里。

> 来源：https://www.w3.org/2026/05/webextensions-wg-charter.html

### 9.2 规范本体：骨架草案，关键章节是空的

`https://w3c.github.io/webextensions/specification/index.html`（Draft CG Report，**2026-09-30**）
页面顶部原文：**"It is not a W3C Standard nor is it on the W3C Standards Track."**
连 Abstract 都还是 `[Placeholder] Abstract.`

实际覆盖情况（逐节核对）：

| 章节 | 状态 |
|---|---|
| 文件结构（manifest.json / `_locales`） | ✅ 有内容 |
| manifest 键规则（未知键必须忽略、类型不符必须忽略） | ✅ 有内容 |
| 执行上下文 / isolated worlds | ✅ 详细 |
| extension origin（`chrome-extension` / `moz-extension` / `safari-web-extension`） | ✅ 有内容 |
| content scripts 字段 + 注入算法 | ✅ 详细 |
| URL 匹配算法（18.1 / 18.2） | ✅ 详细 |
| IDL 定义 | ⚠️ **只有两个 enum**：`RunAt`、`ExecutionWorld` |
| **`background` / service worker 模型** | ❌ **空**。13.1 只有标题；2.2.9 只有 "This key may be present." + 待办 issue #282 *"Specify background scripts."* |
| **storage** | ❌ **全篇未出现** |
| **messaging** | ⚠️ 只有 `externally_connectable` 清单键；`runtime.sendMessage` / `tabs.sendMessage` / Port 长连接都没定义 |
| **CSP** | ❌ 只有标题 |
| **host permissions** | ❌ 只有标题 |
| **web accessible resources** | ❌ 只有标题 |
| localization | ❌ 待办 issue #62 |
| 版本号处理 / 安全风险分类 / 与 web 交互 | ❌ 只有标题 |

`window.browser` 那份独立规范（2026-08-24）更直白——`interface Browser { }` **故意留空**，
原文：*"The specifics of what APIs within window.browser are at present intentionally undefined,
and are left up to User Agent implementation."*

### 9.3 所以 Chrome 148 的 browser 命名空间统一了什么？

**只统一了"从哪个全局对象上取 API"，没统一任何 API 的行为。**
`browser.tabs === chrome.tabs` —— 同一个对象，Chrome 的实现。`browser.sidePanel` 在 Firefox 上
照样是 `undefined`，`browser.storage.local` 的上限在 Safari 上照样是 5MB。

### 9.4 对本项目的直接结论

本项目踩过的每一个坑，**恰好都落在标准空白区**：

| 本项目踩的坑 | 规范状态 |
|---|---|
| Firefox event page vs Chrome service worker | ❌ background 模型未规范（issue #282） |
| 默认 CSP 把 `ws://` 静默升成 `wss://` | ❌ CSP 章节空 |
| `moz-extension://<随机 UUID>` 无法进白名单 | ⚠️ origin 有定义，但"是否每机随机"是 UA 实现决定 |
| LNA 是否约束扩展 | ❌ 不在扩展规范里，是 Blink 的 LNA 规范 |
| `data_collection_permissions` / AMO 上架要求 | ❌ charter 明确 out of scope |
| popup 还是 sidePanel | ❌ charter 明确 out of scope |

**结论：分 target 生成 manifest 不是"过早优化"，而是标准缺位期的唯一解。**
至少到 2028-05 charter 结束前都别指望靠标准消除这批差异——而且即便届时写完，
交付形态也只是 CR Snapshot。

### 9.5 标准里唯一能借力的一条

第 2 章规定：**规范未定义的 manifest 键，实现必须忽略；已定义但 JSON 类型不符的键也必须忽略。**

这条正是分 target 能成立的底层保证——Chrome 忽略 `browser_specific_settings`，
Firefox 忽略 `minimum_chrome_version`，两边各自安静地跳过对方的字段。
换句话说：**W3C 标准化的不是"扩展长什么样"，而是"各家怎么和平共处"。**
